# Module 2 Demo Runbook

This runbook now includes the full REST API vertical-slice demo that was missing in v1.

## Demo principles

Narrate decisions, not clicks.

* “I am asking for a plan because this touches multiple files.”
* “I am narrowing the plan before I let the assistant edit.”
* “Generated tests are drafts; the assertions still need human review.”
* “AI can review this diff, but it does not approve it.”

## Demo 1 — Full vertical slice: build part of the REST API with AI assistance

**Core time:** 45–60 minutes  
**Expanded time:** 75 minutes  
**Required:** Yes

### Purpose

Show the full Module 2 loop on a real mini-repo:

Frame → Plan → Prompt → Execute → Verify → Reflect.

### Setup

Open `work\_items\_api\_starter/` in the IDE. Keep these files visible:

```text
app/main.py
app/models.py
app/repository.py
tests/test\_work\_items\_api.py
```

Run:

```bash
pytest -q
```

Expected result: failing tests because repository behavior is intentionally incomplete.

### Step 1 — Frame the task

Instructor says:

> The API contract and tests are already here. Our job is not to let AI invent the app. Our job is to use AI to implement the missing repository behavior in a bounded, reviewable way.

### Step 2 — Ask for a plan, not code

Prompt:

```text
Do not write code yet.

Inspect this FastAPI Work Items API project and propose a minimal implementation plan for making the CRUD tests pass.
Include:
1. current behavior visible in the code
2. files likely to change
3. files that should not change
4. missing repository behavior
5. implementation steps
6. tests and verification commands
7. assumptions and risks
Do not edit files yet.
```

Expected answer:

* Main file to change: `app/repository.py`.
* Tests to use: `tests/test\_work\_items\_api.py`.
* Endpoint paths and Pydantic models should remain stable.
* Need create/list/get/update/delete and filtering.
* Verification: `pytest -q`, optionally `python -m compileall app`.

Likely AI deviations:

* Suggests rewriting `app/main.py` unnecessarily.
* Suggests changing tests before implementation.
* Suggests switching to SQLAlchemy.
* Suggests adding pagination now.

Instructor response:

```text
Revise the plan. Keep the first implementation slice limited to app/repository.py.
Do not change endpoint paths, models, tests, dependencies, or response shapes unless a failing test proves it is necessary.
```

### Step 3 — Implement create and list first

Prompt:

```text
Implement only the repository create\_item and list\_items behavior.
Constraints:
- edit app/repository.py only
- use the existing SQLite connection helpers
- use parameterized SQL
- keep deterministic ordering
- do not add dependencies
After editing, summarize the diff and tell me which tests to run.
```

Run:

```bash
pytest -q tests/test\_work\_items\_api.py::test\_create\_work\_item\_returns\_payload\_and\_timestamps \\
          tests/test\_work\_items\_api.py::test\_list\_work\_items\_empty\_and\_then\_ordered
```

Expected behavior:

* Create test passes.
* List test passes.
* Other tests still fail.

If the AI changes endpoint code, revert or ask:

```text
Stop. Revert unrelated endpoint changes. Keep this slice limited to repository behavior.
```

### Step 4 — Implement get/update/delete/filtering

Prompt:

```text
Continue with the next repository slice: get\_item, update\_item, delete\_item, and status/priority filtering.
Constraints:
- edit app/repository.py only
- preserve existing fields during partial updates
- return None/False for missing IDs so endpoints can raise 404
- use parameterized SQL
- keep ordering deterministic
After editing, summarize the behavior changes and verification command.
```

Run:

```bash
pytest -q
```

Expected result: tests pass after a correct implementation.

### Step 5 — Test the tests

Open `review\_exercises/weak\_generated\_tests.py`.

Prompt:

```text
Review tests in review\_exercises/weak\_generated\_tests.py as if they were generated by an AI assistant.
Find weak assertions, missing edge cases, misleading names, and behavior that is not actually proven.
Suggest stronger assertions without changing production code.
```

Expected findings:

* status-code-only assertions;
* filter test creates only matching data;
* delete test never verifies the item is gone;
* no payload validation;
* misleading confidence from test names.

Show `review\_exercises/corrected\_generated\_tests.py` as a fallback or solution.

### Step 6 — Diff review and PR summary

Prompt:

```text
Review the current diff as a review aid, not as approval.
Give me:
- behavior changes
- risk areas
- missing tests
- backward compatibility concerns
- security/privacy concerns
- manual checks still needed
- a concise PR summary
```

Instructor debrief:

* Which comments were useful?
* Which comments were generic?
* What did the human reviewer still need to decide?

### Step 7 — Reflection

Ask students:

* What did AI make faster?
* What did AI make riskier?
* Which prompt constrained the change most effectively?
* Which AI suggestion would you reject?

## Demo 2 — Debugging without guessing

**Core time:** 15–20 minutes  
**Optional:** No, but can be shortened.

Use any failing test from the starter. Prompt:

```text
Do not patch yet.
Analyze this failing test and stack trace.
List the top 3 likely causes, evidence for and against each, the smallest check to confirm, and the first fix you would try.
```

Teaching point: debugging is evidence-building, not random patching.

## Demo 4 — API client and comments/docstrings

**Core time:** 20–25 minutes  
**Required topic, compact treatment:** API clients and comments/docs are in the syllabus.

Prompt:

```text
Generate a small Python httpx client for the Work Items API.
Include create, list, get, update, and delete methods.
Use explicit timeouts.
Raise useful exceptions for non-2xx responses.
Add docstrings that explain intent, not comments that merely repeat the code.
Do not add authentication or retries yet.
```

Review checklist:

* Timeout present?
* Errors handled clearly?
* Response JSON shape assumptions visible?
* Comments useful or redundant?
* No fake auth/secrets?
* Tests possible with `httpx.MockTransport`?

Show the solution client in `work\_items\_api\_solution/app/client.py`.

## Universal fallback

If live AI fails:

1. Use the prompt examples above.
2. Open `work\_items\_api\_solution/app/repository.py`.
3. Compare it to `work\_items\_api\_starter/app/repository.py`.
4. Run the solution tests.
5. Continue the class around plan/diff/test review.
