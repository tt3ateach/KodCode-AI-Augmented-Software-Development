# Module 2 Prompt Cookbook

Use this cookbook during demos, labs, homework, and instructor preparation.

## Required core prompts

### 1. Planning before code

```text
Do not write code yet.

Task:
<task>

Context:
<repo/module/ticket/test failure>

Constraints:
- keep public APIs stable unless approved
- prefer the smallest safe change
- identify tests to add or update
- call out assumptions and unknowns
- keep the implementation reviewable

Output:
1. Restate the task
2. Clarifying questions or assumptions
3. Files likely to change
4. Files that should not change
5. Step-by-step plan
6. Risks and edge cases
7. Tests to add or update
8. Verification commands
```

### 2. Existing-codebase map

```text
Read the repository and produce a read-only architecture map.
Do not suggest changes yet.

Include:
- main entry points
- important modules and responsibilities
- data flow
- test commands
- conventions you infer
- assumptions you cannot verify from the repo
```

### 3. Bound the implementation slice

```text
Given this architecture map, identify the smallest safe implementation slice for:
<feature/bug>

Before editing, list:
- files you expect to touch
- why each file is involved
- files that should not be touched
- risks and rollback notes
- tests that should fail before the fix and pass after it
```

### 4. Implement one step

```text
Implement only step <n> of the approved plan.
Keep the diff small.
Do not refactor unrelated code.
After the change, explain what changed and what tests should now pass.
```

### 5. Debug without guessing

```text
Do not jump straight to a fix.
List the top 3 likely causes of this failure.
For each cause, include:
- evidence that supports it
- evidence against it
- the smallest check or test to confirm it
Then recommend the first thing to try.
```

### 6. Generate tests

```text
Write pytest tests for <function/endpoint>.
Cover:
- expected behavior
- validation failures
- edge cases
- regression cases related to the bug

Rules:
- use existing fixtures
- keep assertions explicit
- tests must prove behavior, not implementation details
- do not change production code unless a test exposes a real bug
```

### 7. Test the tests

```text
Review these tests as if they were generated by an AI assistant.
Identify:
- assertions that do not prove the behavior
- tests that only check status codes but not payloads
- missing edge cases
- misleading test names
- duplicated or brittle tests
Suggest improved assertions.
```

### 8. AI-assisted code review

```text
Review this diff.
Do not approve it.
Give me a review aid with:
- behavior changes
- risk areas
- missing tests
- security/privacy concerns
- backward compatibility concerns
- questions a human reviewer should ask
- suggested follow-up checks
```

### 9. PR summary

```text
Draft a PR summary for these changes.
Include:
- what changed
- why it changed
- how it was tested
- known limitations
- reviewer focus areas
```

### 10. Privacy/leakage check

```text
Before using AI help on this task, identify any sensitive data in the prompt, files, logs, screenshots, stack traces, or examples.
Suggest a redacted version that preserves technical value without exposing secrets, customer data, tokens, or proprietary details.
```

## Optional

### Optional A. Terminal-agent command review

```text
Before running any command, explain:
1. what it does
2. why it is needed
3. what files or systems it can modify
4. how to undo or inspect the result
Wait for approval before running it.
```

### Optional B. Cloud-agent task brief

```text
Convert this work into an issue-shaped task for a coding/cloud agent.
Include acceptance criteria, files likely in scope, files out of scope, tests, risks, and a PR review checklist.
Do not assume the agent can merge or deploy.
```

### Optional C. Advanced API-client hardening

```text
Review this generated API client for production hardening.
Focus on timeouts, retries, error typing, authentication boundaries, logging, docstrings, and whether comments add useful intent.
```
